## Problem

Phase 2 needs a durable data model that stores source state rather than derived draft views.

The app already has pure helpers for:

- hydrating a `Draft` from league settings and pick history
- serializing/parsing ranking snapshot JSON

The next step is to define how those source inputs will be stored. The schema must support default and non-default league configurations without hard-coding 12 teams, 16 rounds, fixed roster slots, draft order length, or empty future picks.

## Proposed Schema Shape

Use names that fit Prisma conventions, but keep the schema close to this shape:

```prisma
enum DraftStatus {
  NOT_STARTED
  IN_PROGRESS
  COMPLETE
}

model Draft {
  id                String          @id @default(cuid())
  name              String?
  status            DraftStatus     @default(NOT_STARTED)
  leagueSettings    Json
  userTeamId        String
  rankingSnapshotId String
  rankingSnapshot   RankingSnapshot @relation(fields: [rankingSnapshotId], references: [id])
  picks             DraftPick[]
  createdAt         DateTime        @default(now())
  updatedAt         DateTime        @updatedAt
}

model RankingSnapshot {
  id        String   @id @default(cuid())
  rankings  Json
  drafts    Draft[]
  createdAt DateTime @default(now())
}

model DraftPick {
  id         String   @id @default(cuid())
  draftId    String
  draft      Draft    @relation(fields: [draftId], references: [id], onDelete: Cascade)
  pickNumber Int
  playerId   String
  createdAt  DateTime @default(now())

  @@unique([draftId, pickNumber])
  @@index([draftId])
}
```

Expected behavior:

- `leagueSettings` stores the full typed settings source shape as JSON.
- `rankings` stores the ranking snapshot JSON produced by the mapper.
- `DraftPick` rows represent only made picks.
- Empty future picks are not stored.
- Draft size, team count, roster slots, round count, and draft order are derived later from `leagueSettings`, not stored as fixed schema columns.
- `DraftPick.pickNumber` identifies where a made pick belongs in the generated draft order.
- `DraftPick.playerId` stores the selected ranking/player ID used by hydration and recommendation logic.

## Implementation Steps

1. Add Prisma dependencies and scripts.
   - Install `prisma` as a dev dependency.
   - Install `@prisma/client` as a runtime dependency.
   - Add scripts such as:
     - `prisma:validate`
     - `prisma:generate`
     - `prisma:migrate:dev`
   - Keep existing app scripts unchanged.

2. Add `prisma/schema.prisma`.
   - Use `provider = "postgresql"` for the datasource.
   - Use `env("DATABASE_URL")` for the connection string.
   - Add a Prisma client generator.
   - Add `DraftStatus`, `Draft`, `RankingSnapshot`, and `DraftPick`.

3. Model persisted source state.
   - Store league settings as JSON.
   - Store ranking snapshots as JSON.
   - Store pick history as made-pick rows only.
   - Link drafts to ranking snapshots.
   - Add timestamps that support future listing and history views.

4. Add constraints and indexes.
   - Add a unique constraint for one made pick per draft pick number.
   - Add an index for loading pick history by draft.
   - Use cascade delete from draft to pick history if the draft is deleted.
   - Avoid constraints that assume MVP team count, round count, roster size, or draft size.

5. Validate.
   - Run `npm run prisma:validate`.
   - Run `npm run prisma:generate`.
   - Run `npm test`.
   - Run `npm run lint`.
   - Run `npm run build`.
